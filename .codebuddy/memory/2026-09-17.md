### ⚠️ 修正：我此前的「链不完整」推断是错的（实测推翻）

我最初基于「存在 `create_all + stamp`」**推断**本项目迁移链很可能与 MineAdmin 一样缺建表语句，并据此在规则文件里写下「本项目当前为违规状态」。
**用户要求实测验证后，该推断被推翻。**

**实测方式**：`alembic/env.py:27` 支持 `ALEMBIC_DB_URL` 环境变量覆盖（无需改 `.env`），指向临时库跑链。

**链路**：单头线性 4 步 `582670eaa9ea` → `1e99a7fcad44` → `f9c9610dbf51` → `30bcfbeddb70`

| 场景 | 结果 |
|------|------|
| 空库 `upgrade head` | ✅ 4 步跑通；**19 表 / 19 模型表，集合差异 0，列差异 0** |
| `downgrade base` | ✅ 4 步降级；表数归 0 |
| 往返后结构 | ✅ 19 表零列差异 |
| 老库带数据升级 | ✅ 业务数据保真（`olduser` / `o@x.com`） |

**结论：迁移链完整可用，不存在缺建表语句缺口。**

**教训（与 MEMORY 3.1 同源）**：我把「存在某反模式」**推断**成了「必然存在某后果」，并写进规则文件用「违规状态」这种肯定措辞。
**反模式的存在 ≠ 反模式的后果已发生。** 前者可 grep 确认，后者必须实跑。
这与 MEMORY 3.1「用验证的语气说未经验证的结论，比完全不验证更危险」是同一类错误——**我用了「本项目当前为违规状态」这种断言语气**，而当时只验证了「有 create_all」，没验证「链跑不通」。

**修正动作**：规则文件标题去掉「违规状态」，改为区分「链已实测完整」与「机制仍有隐患」；记忆同步修正。

### 测试数据构造的两次失败（`user` 表 NOT NULL 约束）

插入老库测试数据时连错两次列名/约束：`hashed_password`（实为 `password`）→ `sex` NOT NULL。
**教训**：构造测试数据前应先 `inspect().get_columns()` 查真实 schema，**不要凭字段名推测**（同 MEMORY 3.3「用真实数据不凭字段名推测」）。
