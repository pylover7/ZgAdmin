### 实测发现（重要，纠正了一个错误归因）

**① 补列 SQL 只带类型、不带约束（已实跑验证）**

`_repair_dirty_tables()` 的补列实现是 `column.type.compile(dialect)` → `ALTER TABLE "t" ADD COLUMN "c" INTEGER`。模型的 `nullable=False` 与 default **都不会带出**，补出来的列恒为**可空、无默认值** → **库结构静默偏离模型定义**。

- **同时推翻了本次过程中的一个错误归因**：我先前据「症状相似」（已知 SQLite 上 `ADD COLUMN ... NOT NULL` 在表非空时失败）**推断**自愈会撞 `NOT NULL` 抛错，并已写进规则文件。实测 `department.status`（模型为 `nullable=False`）编译结果仅为 `INTEGER`，补列**成功不抛错** → 该归因完全错误，已改写为真实现象。
- **教训**（已固化进 `MEMORY.md` 3.8）：**「症状相似」提供的是排查方向，不是结论**；归因必须实跑验证后再写。
- **代价**：错误归因写进规则后，会污染同一条规则里的**其他正确结论**（本次「自愈函数无异常保护」是对的，被错误的失败路径示例拖累）。

**② 自愈函数确实无异常保护**（结论保留）：`_repair_dirty_tables()` 自身无 try/except，内部 SQL 抛错会冒泡打断 `init_data` → 服务启动失败。故**不得承诺「自愈失败不影响使用」**。

**③ 前端 XSS 面真实存在**：改造前 `escapeHtml` 全仓库不存在；`dangerouslyUseHTMLString: true` 3 处，其中 2 处消息体纯文本（开关多余且直接内插 `row.username`/`row.name`），1 处确需 HTML 且 `release_url` 落在 `href` 上下文。
